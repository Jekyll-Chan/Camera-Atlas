# Camera Atlas 内核流水线设计

2026-11-19。状态：阶段性实施设计。已增加本地持久任务、查询/重试、页面恢复与持久输出；全球地点搜索、自动选区、完整覆盖契约和公众部署尚未实现。本文的完整版本化接口仍是设计，实际已实现接口见 Mobile-Experience.md。现有 UI 保持全英文与衬线字体；最终公众入口目标见 [Public-Service.md](Public-Service.md)。

## 当前可用范围

| 环节 | 实际情况 | 下一步 |
| --- | --- | --- |
| 图片读取 | 规范化 EXIF 方向、保留 ICC；网页接受 JPG/PNG/WebP，原文件已持久保留 | 预览与原尺寸分离；网页 HEIC 接入 |
| 地点 | 网页仅两个内置地点；CLI 有 Nominatim 兼容查询与歧义结果 | 网页搜索服务、带来源的候选、服务端确认记录 |
| 选区 | 手工涂选、擦除、撤销；区域蒙版可含主体空洞 | 蒙版版本与底图绑定；以后增加可编辑的自动建议 |
| 窗口 | 可按选区比例扩大长轴，两个轴保持统一比例 | 自动选取合理地理跨度，并输出可复核的窗口计划 |
| 数据 | 网页固定离线数据与半径；CLI 可查少量 OSM ways、读取 GeoJSON/DEM | 按窗口取数、声明覆盖范围、处理关系与不完整响应 |
| 合成 | 真正透明图层；选区外像素校验；来源记录 | 统一预览与原尺寸输出的场景参数 |
| 下载 | 工作目录持久保存，重启后可下载；网页恢复最近任务 | 公众访问隔离、明确过期时间 |
| 运行 | 已有持久有界队列、阶段状态和显式重试 | 取消、细分提供器错误、完整版本化与公众适配器 |

现有自动测试证明特定输入下的合成、地理和像素规则，不能证明任意地点的线上流水线已经可用。

## 核心顺序

照片入库 → 准备并固定干净底图 → 确认地点 → 确认选区 → 规划地理窗口 → 获取完整范围数据 → 透明地图渲染 → 像素与地图检查 → 预览 → 原尺寸导出。

地点确认和选区编辑可以并行准备；只有二者都有效，才能规划地图窗口并开始取数。用户界面仍是 Photo / Place / Map / Save，不把内部阶段全部变成用户操作。

## 借鉴 Agensi workflow：两个入口，一套内核

依据 2026-11-19 查阅的官方资料：Agensi 把技能说明交给用户的 agent 执行，并不替 Camera Atlas 运行本地渲染器。技能主文件先加载，其他文本按需读取；缺少必要工具时先说明限制。参见 [工作方式](https://www.agensi.io/docs/how-it-works) 与 [技能加载机制](https://www.agensi.io/docs/how-agents-load-skills)。

Agensi 另有工具调用机制：查找工具、报价、执行，慢任务通过 `check_job` 获取进度和文件链接。这是它的工具服务，不能等同于任意 SKILL.md 已经拥有托管执行能力。参见 [官方工具说明](https://www.agensi.io/docs/tools)。本项目借鉴其任务交付方式，不接入付费工具，也不把 Agensi 账户设为手机网页的使用前提。

| 可借鉴的机制 | Camera Atlas 的落地方式 |
| --- | --- |
| 先匹配需求与能力 | 核对照片、地点、可用引擎、数据源；明确可渲染或缺少什么 |
| 按需读取步骤与参考资料 | 主 Skill 保持短小，按实际需要读取清洗、地理、区域铺满和导出规则 |
| 工具负责具体执行 | 将取数、投影、蒙版裁剪、合成和检查做成共享内核操作 |
| 慢任务返回任务 ID | 网页和 Skill 都获取阶段状态，完成后领取同一份版本化产物 |
| 交付成品与运行反馈 | 保存来源报告与具体失败阶段；用户不用重新上传已有照片 |

共享关系：

```text
Agensi Skill → 用户的 agent → 本地 CLI 适配器 ─┐
                                            ├→ 同一工作流与渲染内核
手机网页 → 应用 API → 后台任务适配器 ─────────┘
```

这是拟实施结构，当前两个入口尚未共用完整任务系统。任务恢复、区域覆盖检查和原图保护是 Camera Atlas 自己要实现的能力，并非 Agensi 已提供的保证。

每个步骤约定输入版本、输出产物、通过条件、可恢复错误和失效依赖。只有产物满足通过条件才能进入下一步；agent 的文字判断不能替代运行结果。已有 `clean_base` 必须复用，不因新一轮对话重新清洗。未取得地图数据时不能用无地图照片冒充完成。

AI 可辅助理解用户意图、建议地图模式和可编辑选区；坐标解析、地理范围、地图几何、像素合成和文件输出由可验证程序执行。自动选区尚未实现时继续使用人工涂选，不让缺少模型阻断整个流程。

同一任务固定引擎、规则和输入版本，避免技能更新后改变正在执行的结果。Agensi 每次使用加载最新发布内容，因此适配器启动时仍需验证引擎能力；当前旧下载锁定版本缺少 `region_mask`，不能被任务系统当作支持区域铺满的引擎。

先保留一个 Camera Atlas Skill 与模块化参考文件，无需为了编排拆成多个商品。下一步实施优先完成持久任务和数据覆盖契约，再接真实地点服务；不新增界面步骤。

### 1. 照片入库

- 保存不可变原始文件、内容哈希、规范化底图、尺寸、ICC 与内部 EXIF 信息。当前网页已保留原文件；完整版本/元数据记录仍待实现。
- 小预览只用于显示；导出仍以原尺寸底图为依据，不把小预览放大当高清成品。
- EXIF 方向只规范化一次。用户有意横置在竖屏中的构图保持不变。默认保留原比例，另设画布要求时通过明确的留边方案处理。
- 先限制解码后的像素数量和内存，再解码。错误提示给出可操作的原因。

产物：`asset_id`、原始文件、`base_revision`、规范化尺寸、预览、色彩信息。

### 2. 准备干净底图

- 普通照片直接成为干净底图，自动跳过清洗步骤。
- 有截图 UI 或旧文字时，先形成修复区域与清洗预览；用户确认后固定新的 `base_revision`。
- 清洗属于独立可选处理，不允许制图阶段重新生成整张照片。被遮挡细节无法保证真实恢复，需要留下修复记录。
- 更换底图、旋转或裁切使旧蒙版失效。单纯调整地图无需再次清洗。

产物：不可变 `clean_base`、修复蒙版/记录（如有）。

### 3. 地点解析与确认

- 显式输入优先；EXIF GPS 可作为候选。两者冲突时展示冲突，不悄悄换地点。
- 地名搜索返回候选 ID、名称、行政区、地区边界、来源与精度。即使只有一个候选，网页仍要求用户确认。
- 服务端存储确认记录，生成 `location_revision`。提交渲染时传这个记录 ID，不依赖客户端一个 `confirmed: true` 布尔值。
- 地区中心是地区中心，使用空心红圈；只有可信拍摄 GPS 使用实心标记。不通过大模型回忆来补坐标。
- 名称变化撤销旧确认。地图地点与照片 EXIF 不同是可解释的用户选择，不自动改写原图。

产物：已确认地点记录，包含来源、精度和候选身份。

### 4. 选区与地图窗口规划

蒙版以规范化底图坐标为准。手机显示坐标必须映射回原尺寸。白色允许地图，黑色保护主体。边缘半透明处理采用明确定义，不能让预览与导出使用不同阈值。

选区外框为 W×H，短轴地理跨度为 S：

- 每米像素数 `k = min(W, H) / S`。
- 地理窗口宽高分别为 `W / k`、`H / k`。
- 长轴扩展真实地理范围，不能对现有地图做非等比拉伸。
- 地点标记尽量落在选区内部；移动艺术锚点不改变地点坐标，也不旋转照片。
- 地图窗口覆盖完整外框，最终按不规则蒙版裁剪。不再使用固定方形内框、20% 上限或空白底栏。

新增“窗口计划”应先于任何地图请求产生，记录选区哈希、投影、范围、比例、地图模式、图层列表、地理跨度选择依据。推荐地理跨度结合地点边界、数据分辨率和实际地物分布，不能给所有城市使用同一个常量。选区发生变化后重算范围，再检查缓存是否足够。

### 5. 地图取数与覆盖校验

此阶段是解决“窗口变大、地图仍缩在中间”的关键。

- 城市优先街道/步道/水系；湖海使用真实水体及岸线；山地等高线必须来自真实 DEM。模式由实际可用地理数据决定，不凭装饰效果编造线条。
- 数据提供器接收窗口的真实地理范围，返回数据、查询/数据集覆盖边界、时间、来源、许可、响应完整性和支持的地物类型。
- 缓存索引以地点范围、数据源版本和图层类型为依据。只有缓存的已声明覆盖范围包含新窗口时才复用；不能因缓存内有几条道路就认定足够。
- 覆盖边界不能从现有地物的最小外接框推断。真正没有道路的水面与“根本未查询到此处”是两回事。
- 空间范围覆盖与地物完整性分别记录。例如请求覆盖整个湖区，不意味着解析器已组装水体 relation。当前 ways-only 解析不足以保证大型湖泊完整。
- 对多边形关系、孔洞和跨范围要素采用可验证的组装/裁剪，失败时标记不完整，不画假线闭合。
- 获取失败后，只重试可恢复错误；尊重上游限流并设置总尝试/时长上限。不轮换公共主机绕过限流。超大窗口转向适当的区域数据集。
- 缺数据不能返回一张原图并标记成功。返回 `needs_data`，保存此前的照片、地点和选区。

两层验收：先检查数据获取范围与解析完整性，再检查真实地图几何在选区内的分布。后者不能替代前者，也不能把稀疏真实地理判为必须填满的空白。

### 6. 场景渲染与独立合成

建立一个与输出像素尺寸无关的地图场景：真实几何、投影、范围、地点锚点、标签、线条样式、字体、署名与归一化选区。预览和导出使用同一场景/版本。

- 地图层采用确定性制图，不调用生成式模型重画背景。
- 地图先覆盖整个窗口，再裁入蒙版；主体保持原样。
- 文字、比例尺、方向与署名必须可读且完整；署名不能被主体保护蒙版吃掉。放不下时给出可解释的调整提示。
- 预览可降低图片分辨率，但几何范围和标签选择保持一致。导出使用原尺寸底图重新绘制，不上采样预览。

产物：场景记录、独立透明地图、预览或原尺寸合成图。

### 7. 检查、预览与导出

自动检查包括尺寸/方向、原图色彩信息、选区外与保护区像素一致性、真实几何是否存在、引用来源是否齐全、地理范围与比例、署名完整性。

地图空间分布检查只统计几何，排除文字、标记、署名。不得以 PNG 尺寸、图层外接框或单一“覆盖百分比”宣称铺满。大片空白要结合源覆盖范围区分取数缺失与真实稀疏；需要人判断时返回 `needs_review`。

通过后进入可预览状态。用户调整透明度/样式时只重做渲染；修改选区时重做窗口与覆盖检查；修改地点时重做地点后的各阶段。生成新版本期间，旧结果可作旧版本对照，但下载按钮不能把它冒充当前设置的结果。

用户点击 Save 后按同一场景导出原尺寸 PNG，附透明图层、有效蒙版和来源报告。下载对象绑定已完成任务版本与所属会话，有明确保留期限。

## 任务与接口设计（待实施）

采用一个后台协调器维护可持久化任务记录。第一阶段本地可用 SQLite 和受限工作进程；公众部署再接适合实际负载的队列与文件存储，避免先堆基础设施。

建议任务状态：

`queued → planning → fetching → rendering → verifying → ready`

分支状态：`needs_input`、`needs_data`、`needs_review`、`failed`、`cancelled`。`failed` 记录可恢复阶段与简短错误码；用户重试复用已经通过检查的产物。任务取消须传播到网络/渲染阶段，不能只把页面上的旋转图标藏起来。

| 接口 | 用途 |
| --- | --- |
| `POST /api/assets` | 保存原图并返回底图/预览记录 |
| `GET /api/places?q=...` | 用户提交搜索后查候选；提供器相关限流在后台统一处理 |
| `POST /api/location-confirmations` | 将候选与精度确认为服务端记录 |
| `PUT /api/assets/{id}/region` | 保存与底图版本绑定的蒙版 |
| `POST /api/jobs` | 提交版本快照，返回任务 ID；不长时间占住上传请求 |
| `GET /api/jobs/{id}` | 返回阶段、可操作提示、结果和有限错误信息 |
| `POST /api/jobs/{id}/cancel` | 取消未完成任务 |
| `POST /api/jobs/{id}/exports` | 使用已确认场景导出原尺寸文件 |

任务输入摘要覆盖底图版本、地点确认版本、蒙版、地理窗口、数据源快照、渲染样式和引擎版本。相同输入可复用，变化后的旧任务结果不能覆盖新任务。网络令牌只保存在后台，前端不提供任意服务器地址或本地文件路径。

界面只需要阶段词如 Preparing / Mapping / Rendering / Ready。失败就地保留输入，提供 Retry / Edit，而不是把所有问题显示成一句泛化的 Something went wrong。

## 数据服务选择

当前内置离线样例可用于可重复验证。下一阶段应先把带来源的区域包接到统一提供器接口，随后接入明确支持应用用途的地点服务与地图数据服务，或自建实例。地图提供器只收到地点/范围，通常无须上传照片。

公共 Nominatim 有应用总计请求速率、禁止自动补全、缓存及开发者明确选择等限制，不能被默认为全球无限量搜索后台。参见 [官方政策](https://operations.osmfoundation.org/policies/nominatim/)。公共 Overpass 官方也不建议普通面向大众的应用长期将公共实例作为后台，区域提取/自建或合适服务应成为正式数据来源。参见 [官方使用说明](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html)。具体供应商、运行费用和账户配置属于上线选型，当前未开通或付费。

## 实施顺序与验收门槛

### A. 先让当前闭环可恢复

拆分 `MobileWorkspace.create_render` 的同步流程，建立持久资产、版本、窗口计划、数据提供器接口、结构化失败与任务状态。先接现有真实样例验证，不把新增队列包装成已经支持全球地点。

已完成 A 的任务交付部分：本地 SQLite 队列、输入快照、原文件持久保存、状态查询、显式重试、请求去重与浏览器最近任务恢复。运行任务遇重启标为 interrupted，排队任务可继续；原始渲染仍为单个内核调用。窗口计划、完整资产版本、数据提供器接口和取消尚未完成。

验收：刷新页面可恢复任务；取数失败可重试而不重传；改选区使旧输出失效；无地图不进入 ready；重启后资产和任务关系正确。

### B. 打通真实地点与完整地理范围

接入地点候选/确认、真实地图源与范围缓存；补齐所需水体关系与 DEM 路径。以非内置地点完成独立端到端验收。

验收用例：东京站的横向天空、八坂神社侧向天空、十七孔桥水面、赛里木湖地形。使用已有授权的干净底图与地点，不把私人图片提交公开仓库。覆盖数据完整性、长条选区、主体空洞、同名地点、稀疏地理、超时和来源缺失。

### C. 再增加自动建议与公众运行能力

自动区域建议必须可修改，人工涂选始终可用。完善 HEIC、批量、任务取消、文件生命周期、真实手机相册/下载及部署容量。先证明单张照片的稳定成功率，再增加批量入口。

最终功能验收：用户上传非样例照片、确认非内置地点、选区后获得有真实来源的地图预览，下载原尺寸成品；地图覆盖选定地理窗口，照片方向/色彩与受保护区域保持不变；故障时能明确说明原因并恢复操作。
